# 门户页搜索框：引擎清单在 LuCI 表单，`links.json` 只传模板

- 状态：已接受
- 日期：2026-10-16
- 决策者：cocolight

## 背景

ROADMAP #16 / #17 要求给门户页加搜索：设置页一个开关加引擎选择（#16），门户页上
按空格唤出、回车搜索（#17）。现状是门户页完全没有搜索 —— `portal.js` /
`portal.css` / uci 里都搜不到 search，两项都含从零实现。

搜索是纯前端行为：一个 GET 表单直接提交到第三方引擎的结果页，不需要新 ubus 方法、
不动 ACL、不给 rpcd 添负担。真正要定的是**引擎清单放在哪**、uci 存什么、
`links.json` 带什么。项目对「同一份规则出现两处」有明确态度（`common.js` 里
`maintenance_section` 的注释：两份规则就是两次弄错的机会），引擎清单不能前后端
各写一份。

## 决策

1. **引擎清单只存在于 LuCI 表单**（`general.js` 的 `ListValue`）：Google（默认）、
   Bing、DuckDuckGo、百度，外加「自定义」。uci 的 `search_engine` 存的是引擎的
   **结果页 URL 模板**（`https://www.google.com/search?q=%s`），不是友好键名；
   选「自定义」时存字面量 `custom`，模板改放 `search_url`。
2. **后端只解析与校验**：`portal.uc` 新增 `search_template()`，把 `custom` 解析到
   `search_url`，用与前端逐字相同的表达式 `/^https?:\/\/[^ \t]+%s/` 校验（两道闸，
   与上传限制同规）；校验不过则视为没有模板。
3. **`links.json` 只带解析后的模板**：开关打开且模板合法时烘
   `"search": { "template": "…" }`，否则 `null`。门户前端据此决定是否创建表单，
   自身不持有任何引擎知识。
4. **默认值**：`search_enabled` 缺省视为**关**（沿外观滑块「缺省回落旧行为」的先例，
   升级用户外观不变），随包配置显式写 `'0'`；默认引擎 Google。
5. **交互**（#17）：表单默认隐藏，门户页按空格唤出并聚焦；仅输入框为空时再按空格
   才隐藏；回车提交后在新标签页打开结果页并隐藏搜索框。IME 合成期
   （`isComposing`）不响应空格 —— 中文拼音的空格是上屏键。

## 后果

- 正面：引擎清单单一事实源在表单，`links.json` 契约保持「前端零引擎知识」；
  无新 ubus 方法，ACL 与 `methods` 表不动，`scripts/check.sh` 的 ubus↔ACL 项
  自然通过；手改配置填错模板时页面不带搜索框，而不是把访客的关键词发去一个
  没人选的引擎。
- 负面（明确承认）：uci 里存的是 URL 模板而非键名，手改配置的人看到的是长串
  （可读性尚可，`%s` 语义自明）；「自定义」把任意第三方 URL 交给访客浏览器访问，
  隐私提示只能写在设置页描述里；前端提交用 `window.open` 新标签页，被浏览器
  弹窗拦截时的降级是「什么都不发生」，无错误提示。
- 未变：`generate()` 仍是 `links.json` 的唯一生产者；外观滑块与书签的回落规则
  不变；翻译仍走 `pot`/`po` 两个文件。

## 备选方案

- **后端持引擎表，`status` 下发给表单动态生成 `ListValue`**：不选。表单渲染将
  依赖一次 ubus 调用，失败时下拉框为空，降级路径复杂；换来的是「清单也在后端」，
  但后端并不需要这份清单。
- **uci 存引擎键名，前端持表**：不选。把引擎知识推进门户前端，`links.json` 契约
  从「模板」退化成「键名」，前端要跟着后端表更新，正是要避免的耦合。
- **搜索走后端代理**（如 `luci.portal search` 方法转发请求）：不选。为一个静态
  导航页引入服务端请求转发，扩大攻击面与依赖，与项目「纯静态」定位冲突。

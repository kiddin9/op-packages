# 门户改由主 uhttpd 的子路径提供

- 状态：已接受
- 日期：2026-10-12
- 决策者：cocolight

## 背景

在此之前，门户由 `/etc/init.d/portal` 拉起的**第二个 uhttpd 实例**提供服务，监听
用户自选的独立端口（默认 8180）。这一层的成本与它提供的东西不成比例：

- 为几个 KB 的静态文件常驻第二个进程，还要 procd 用 `respawn` 守着它；
- 需要自选端口，并为此做「是否与主 uhttpd 冲突」的校验与提示；
- 需要在防火墙上再放行一个端口，否则只有路由器本机能访问；
- `status` 不得不扫描 `/proc/*/cmdline` 找 `-h /etc/portal/www` 来确认进程存活 ——
  而「进程存活」与「页面能打开」本来就是两个问题。

## 决策

门户不再有自己的进程与端口，改为**主 uhttpd 文档根下的一个子路径**：

- 页面与素材放在 `/www/portal/`，即主实例 `option home`（默认 `/www`）的子目录，
  访问地址为 `http://<router>/portal/`；
- `portal.uc` 的 `WWW` 指向该目录，且所有交给前端的素材 URL 统一加 `/portal` 前缀 ——
  在子路径下，文档根相对的 `/bg/x.jpg` 会被解析到主文档根而 404；
- `/etc/init.d/portal` 不再 `procd_open_instance`：它只负责**发布 / 撤下**页面
  （刷新模板文件 + 生成 `links.json`）并登记 reload 触发器；
- `enabled` 开关的语义由「停掉守护进程」变为「把页面从 Web 服务器上撤下」：
  移除入口文件与 `links.json`，**保留用户上传的素材**，重新启用即恢复；
- `status()` 去掉 `running` / `pid` / `port` / `listening`，改为
  `published`（入口与 `links.json` 是否就位）、`server_listening`（主实例是否在监听
  任一已配置端口）、`reachable`（两者皆真）。设置页据此显示「可访问」与否，并说明
  是哪一层不满足；
- `url` 不再由后端拼装：浏览器用自身 origin 加 `path` 组合 —— 那才是**正在**提供
  页面的地址，且在反代或非标准端口下依然正确。

## 后果

- 正面：省掉一个常驻进程与一个端口，也不再需要额外的防火墙规则；缩略图与 LuCI
  同源，**「LuCI 走 HTTPS 时缩略图被按混合内容拦截」这条已知限制随之消失**；
  设置页的状态从「进程还活着吗」变成「能不能打开」，并且能区分是哪一层不满足。
- 负面（明确承认）：位置被固定为 `/www/portal` —— 若主实例把 `option home` 改成
  别处，包无法自行跟随，需要人工处理；**暴露面随之变化** —— 页面继承了主实例的
  监听地址与防火墙规则，LuCI 若能从 WAN 访问，门户也从 WAN 可访问，而旧方案里
  未放行的 8180 是打不开的；`enabled=0` 会真的移除入口文件，语义比过去
  「停一个进程」更重；`status` 的字段是**破坏性契约变更**，
  `ubus call luci.portal status` 的使用方需要跟改。
- 未变：不引入任何编译型依赖，门禁仍是 `scripts/check.sh` 一处。

## 备选方案

- **保留独立实例**（即现状）：不选。这正是要解决的问题。
- **保留 `/etc/portal/www`，在 `/www/portal` 放符号链接**：不选。文件位置不必改，
  但要依赖 uhttpd 跟随符号链接（其文档根有路径校验），相当于把一个几乎没用过的
  行为引入安全边界，收益与风险不对等。
- **再加一个 `config uhttpd` 段落**：不选。那仍然是第二个 uhttpd 进程，达不到
  压缩常驻内存的目的。
- **把子路径做成可配置**：不选。目录必须落在主实例的文档根内，而 LuCI 侧的 ACL
  文件白名单是静态的；可配置只会让两者更容易漂移。

# 采用 ADR 记录架构决策

- 状态：已接受
- 日期：2026-10-05
- 决策者：cocolight

## 背景

本项目有几处「看起来只是实现细节、实则一旦改动就大范围波及」的选择：

- 门户前端为什么不依赖 LuCI；
- 为什么 ubus 方法名与 ucode 函数名故意不同；
- 为什么上传校验要做两遍；
- 为什么 `generate()` 读不到浏览器侧的 `uci` 暂存值。

这些约束此前只散落在代码注释和聊天记录里。任何人（包括 AI 助手）改动相关模块时，
既不知道约束的存在，也不知道它为什么存在 —— 于是倾向于「顺手优化」，然后在设备上
表现为难以定位的故障。

## 决策

引入 `docs/adr/`，对每一个此类约束记录一条 ADR：写清背景、决定、后果与被否决的备选
方案。已接受的记录不得修改，需要变更时新增一条并标注取代关系。

## 后果

- 正面：约束有了可检索的落点；AI 助手在 `AGENTS.md` §1 的上下文入口里被引导先读它。
- 负面：新增决策时多一步流程；ADR 可能与代码漂移，因此 ADR 里只写**为什么**，
  具体的「是什么」仍在代码与 `docs/architecture.md` 中。
